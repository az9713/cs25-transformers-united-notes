Serving Transformers: Lessons from Production Inference

A model that reasons correctly when tested alone can become an unusable product when twenty users arrive together. Serving turns a learned conditional distribution into a timed, stateful service. The engineering problem is to preserve an explicit correctness contract while meeting deadlines under uncertain demand.

Charles Frye’s May 28, 2026 lecture proceeds from applications and workload definitions through model and engine choices, hardware, deployment, debugging, observability and optimization. This chapter follows that order. Its running example is an assistant that explains industrial maintenance procedures: a technician needs responsive dialogue, an agent performs several tool calls, and a nightly job extracts structured records from manuals. The procedures and numeric workloads below are invented teaching examples.

How to read the evidence. The recording is represented by local machine transcription, not publisher captions. Available slides resolve diagrams and some names. Paper and engineering-article links support specified mechanisms; dated vendor observations remain vendor observations. Original proofs, simulations and exercises are explicitly local constructions. No GPU or cloud benchmark was performed for this chapter.

1. A forward pass becomes a service

Lecture 00:04

Inference evaluates a trained model without updating its parameters. In an autoregressive language model, the parameters $\theta$ determine a conditional distribution $p_\theta(x_t\mid x_{<t})$ over the next token $x_t$ given the preceding token sequence. Serving adds the machinery that receives requests, schedules these evaluations and returns outputs. A tokenizer converts text into token IDs; a scheduler selects runnable requests; device kernels execute numerical operations; a transport carries results back to a client. A failure anywhere along this chain can spoil the application.

The maintenance assistant’s answer is useful only if it respects the requested equipment revision, cites the correct procedure and arrives while the technician can still act on it. A fast but incorrect response fails the task. A correct response delivered after a timeout also fails. These are separate axes: model quality and service behavior require separate tests. This is the chapter’s first connection to the earlier talks: representation learning, training objectives and generalization determine what the model can do; serving determines when and under which execution contract it does it.

The first two transcript segments contain speaker introduction. The biography is omitted, while the transition to deployment is retained. The official schedule identifies Frye and the lecture date; no inference is made from an uncertain automatic spelling of a name.

2. Demand determines the operational problem

Lecture 01:54

Frye’s opening argument is that inference increasingly consumes serious engineering effort because deployed applications and training-time rollouts repeatedly execute models. In reinforcement learning, a policy may generate many candidates to obtain feedback. In a product, requests arrive when clients need them. Neither case is captured by quoting the time of one isolated forward pass.

For the assistant, a change in shift schedule can cause many technicians to ask similar questions within a minute. The nightly processor can tolerate delayed completion but must finish before the next shift. Agent requests may alternate between short generations and slow external tool calls. These patterns create different allocations of compute, memory and idle time even when they use the same weights.

The lecture describes training as a cost center and inference as part of revenue-generating applications. This is an economic framing, not a universal accounting theorem: inference can support internal research, public services or noncommercial tasks. What transfers across these uses is the need to account for repeated execution, variability and useful outcomes. A sensible service objective is a cost per accepted completed task, not merely a cost per emitted token.

Let $C$ be total resource expenditure in a chosen accounting interval and $N_{\rm useful}$ the number of completed outputs that pass an application-defined quality check. When $N_{\rm useful}>0$, $C/N_{\rm useful}$ measures expenditure per useful completion. It requires stating whether $C$ includes idle allocation, failures, retries and external tools. A system can lower expenditure per token yet increase expenditure per useful completion by emitting longer or less reliable answers.

3. The serving stack and its contracts

Lecture 06:46

The application defines the task; the workload describes incoming work; the model defines numerical computation; the engine implements that computation and its scheduling; hardware provides storage, communication and arithmetic; the deployment system makes replicas available. Debugging and performance analysis connect these layers. Optimizing one layer cannot repair every defect in another.

A replica here is one runnable copy of a model service. Its weights may occupy several devices; replica does not mean one GPU. Several independent replicas can serve different requests concurrently, whereas splitting one model across devices introduces cooperation within a request. This distinction will matter when a single request is too slow, too large for memory, or when the system simply receives too many independent requests.

Write the execution contract before choosing an implementation. For the assistant, it includes the model revision, tokenizer revision, chat template, allowed decoding transformations, stopping rules and tool protocol. Model weights alone do not define a user-visible response distribution. A template change can alter the actual token prefix; a stop-rule change can truncate the response; a sampling change can alter the distribution. A faster implementation is equivalent only with respect to a stated contract.

4. Three workload archetypes

Lecture 08:32

The lecture distinguishes interactive chat, background agents and bulk data processing. Interactive chat emphasizes initial responsiveness and a smooth stream. A background agent emphasizes completion of a multistep job; human reading speed may be irrelevant while the agent waits for a tool result. Bulk processing emphasizes a deadline and aggregate completed work. These are archetypes, not disjoint model classes.

The maintenance application contains all three. A technician asks for a checklist; an agent looks up a parts record and cross-checks a manual; the nightly pipeline extracts inspection dates. The chat response may be short but require strict first-token latency. The agent may generate thousands of internal tokens while the user only sees a final summary. The bulk job may run at high concurrency and accept larger individual delays. A single global latency percentile can conceal which task is suffering.

The recording includes a named document-processing customer example. The teaching case retains the mechanism—bursty conversion of unstructured material into structured records—without treating a promotional case study as an independently reproduced scale benchmark. The important operational distinction is the shape of demand and deadline, not the customer’s identity.

5. From a vague request to an SLO

Lecture 11:16

A service-level objective, or SLO, is a measurable performance target. A service-level agreement, or SLA, is an agreement that may include consequences for violating a target. These terms should not be conflated. “Make the assistant fast” is not an SLO. “For this specified traffic distribution, at least 95% of completed chat requests emit their first token within 0.8 seconds” is measurable, provided the measurement boundary and treatment of failures are explicit.

To prevent a service from improving its statistics by rejecting difficult work, report accepted traffic, offered traffic, errors, cancellation and timeouts separately. If a target concerns all offered requests, a timeout counts as a violation. If a metric concerns completed requests only, say so; it does not establish successful service for all arrivals. For streaming output, define whether timestamps occur at the server, client transport or application display. Network buffering can move apparent latency between layers.

The lecture points to an engine-advisor tool. Such tools can help gather configuration choices, but the general method is independent of a current vendor interface: first specify the workload and quality requirement, then benchmark candidate configurations against that contract. Do not infer that a tool’s recommendation certifies a deployment.

6. Input, output, burstiness and prefix reuse

Lecture 13:15

Characterize each request $j$ by arrival time $a_j$, input-token count $n_j$ and eventual output-token count $m_j$. The input is usually known when the request arrives; the actual generated length depends on stopping rules and model outputs. A requested maximum is a bound, not a prediction. Report the joint distribution of these lengths, because a few long prompts or generations may consume disproportionate resources.

Queries per second describe arrival rate but omit how much work each query requires. Two streams at five queries per second may differ by orders of magnitude in token work. Conversely, tokens per second omit per-request overhead and sequence dependencies. A workload description needs both arrivals and lengths, together with concurrency, prefix similarity and task mix.

Burstiness can be summarized by peak-to-average demand over an explicitly chosen timescale. The transcript’s “average over peak” wording reverses the economically difficult direction. Holding average demand fixed, a higher peak-to-average ratio requires more short-term reserve capacity to avoid queues. The ratio alone does not specify the burst duration; a one-second spike and a one-hour plateau can require different responses.

Prefix reuse means that multiple token sequences begin with identical tokens under the same effective computation. The assistant’s fixed instruction and equipment manual can be shared before each user-specific question. However, visually similar text is insufficient: tokenization, preceding context, positions, model revision and relevant modality state must match. Causal dependence makes a prefix reusable; a matching substring after different earlier tokens generally has different cached states.

7. Four timing quantities that answer different questions

Lecture 16:30

For a completed request, let $t_{j,1}\le\cdots\le t_{j,m_j}$ be token-emission timestamps measured at one consistent boundary, with $m_j\ge1$. Define time to first token $F_j=t_{j,1}-a_j$, inter-token gaps $g_{j,r}=t_{j,r}-t_{j,r-1}$ for $r=2,\ldots,m_j$, and time to last token $T_j=t_{j,m_j}-a_j$. The average time per output token after the first, or TPOT, is defined only when $m_j>1$:

\[ P_j=\frac{1}{m_j-1}\sum_{r=2}^{m_j}g_{j,r},\qquad T_j=F_j+(m_j-1)P_j. \]

This convention agrees with DistServe, PDF pp. 1–2. Other tools may use different denominators; reconcile the definition before comparison. A one-token output has meaningful first/last-token latency but no inter-token gap. Reporting its TPOT as zero silently changes the population average.

Consider arrival at zero and emissions at $0.40,0.42,0.44,0.90$ seconds. TTFT is $0.40$ s, TTLT is $0.90$ s and TPOT is $0.50/3\approx0.167$ s. The individual gaps are $0.02,0.02,0.46$ s. An average hides the final stall. Client rendering may also coalesce several tokens into one transport event; such an event trace measures delivery gaps, not necessarily device iteration times.

A tool-using agent can make several model calls. Its job completion time includes model latency, tool latency, scheduling and dependencies. Adding model-call durations is correct only for sequential calls with no overlap; parallel branches complete according to their critical path. Faster decoding cannot remove an external tool’s fixed delay. Measure both the model service and the overall job.

8. Capacity is useful throughput under constraints

Lecture 19:12

Aggregate token throughput is generated tokens divided by elapsed time. Per-user token rate measures the stream seen by one request. Job completion latency measures a task’s elapsed time. These metrics are related but do not substitute for one another. Increasing batch size can raise aggregate throughput while slowing every individual stream.

Define the feasible arrival rate of a configuration as a rate at which the specified workload meets its joint service and quality targets. A hypothetical assistant target might require both $F_j\le0.8$ s and $P_j\le0.05$ s for at least 95% of completed multi-token chat requests, plus an explicit successful-completion fraction over offered requests. Goodput then counts outputs that satisfy the chosen conditions, rather than every token generated.

The conjunction matters. If TTFT and TPOT each pass for 95% of requests, their joint pass rate may be only 90% when their failing sets are disjoint. The union bound gives joint success at least $1-0.05-0.05=0.90$; independence would give $0.95^2=0.9025$, but cannot be assumed. Measure the joint indicator on each request instead of multiplying marginal percentiles.

Cost efficiency also needs a common denominator. The lecture’s “megatokens per dollar” is a possible bulk metric, but it does not include answer quality, retries or service deadlines unless those are imposed separately. All costs in this chapter are abstract accounting units; no current cloud price is inferred from the talk.

9. Benchmarking one replica without changing the workload

Lecture 20:06

A sequential benchmark submits a request, waits for completion and then submits the next. Its achieved rate is $N/\sum_j T_j=1/\overline T$ when there are no extra gaps between $N$ requests. This is a rate in requests per second; it is not a latency. Low concurrency provides a low-load latency estimate under the tested environment, not a proof of the minimum physically possible latency.

A simultaneous burst of $N$ requests can estimate throughput as $N$ divided by its measured makespan. It must also record each request’s latency. The highest throughput observed in a burst is a result for that experiment, not a universal sustainable capacity. Startup, a finite queue draining after arrivals stop, or a short measurement interval can distort the estimate.

In a closed-loop experiment, clients often submit the next request only after the previous one finishes. A slowing server then reduces offered traffic automatically. An open-loop experiment submits according to an arrival schedule that is independent of previous completions. To study overload, preserve intended arrival times and measure from them; counting only the time after a delayed submission omits waiting induced by the benchmark driver. This is the mechanism behind coordinated omission.

For the maintenance assistant, sweep offered load under a fixed request mixture and include a warm-up policy, measurement horizon and repeated trials. Record successful completions, timeout fraction, queue growth and timing quantiles. Keep cold-start and steady-state experiments distinct. When the queue grows without bound, the observed short-run throughput is not evidence of stable operation at that offered rate.

10. A smooth median can conceal repeated stalls

Lecture 21:42

The lecture shows a nearly unchanged median alongside worsening tail inter-token latency. A percentile is a property of a defined sample distribution. For this chapter’s finite examples, the empirical $u$-quantile uses the sorted sample at rank $\lceil uN\rceil$, with the minimum used at $u=0$. Different interpolation conventions can differ for small samples. Report sample count and convention.

Do not average per-replica p99 values to obtain a fleet p99. Pool the relevant samples with the intended weighting, or merge appropriate histograms. A token-weighted gap distribution gives long responses more weight than a request-weighted distribution of mean TPOT. Both may be useful, but they answer different questions. A request whose mean TPOT is acceptable can still contain one conspicuous pause.

Suppose each of $r$ gaps independently has probability $s$ of exceeding a threshold. The probability of at least one excessive gap is $1-(1-s)^r$. With $s=0.01$ and $r=100$, this is approximately $0.634$. Independence is essential: if all gap events are perfectly correlated, the probability is only $0.01$. In real serving, congestion and scheduling can produce correlated stalls. The example explains why a small per-gap tail can affect many long responses; it does not estimate a real deployment’s event rate.

For service review, record a request-level indicator such as “any gap exceeded 200 ms,” in addition to pooled ITL percentiles and mean TPOT. The threshold is an application choice. Chat readability, voice synthesis and a background agent can require different continuity targets.

11. Choose a model against a quality threshold

Lecture 23:10

Frye distinguishes efficiency-bound deployments from capability-bound deployments. An efficiency-bound task has several sufficiently capable models and emphasizes execution efficiency. A capability-bound task needs the strongest available reasoning or perception and tolerates greater resource use. These are deployment decisions relative to an application’s quality target; a model is not inherently in one category for every use.

The extraction job might accept a small model when equipment revision and date fields are correct under a fixed evaluation. An ambiguous maintenance diagnosis might require a larger model, richer retrieval or a human escalation path. The same model may pass the first task and fail the second. Establish the threshold with representative inputs, rather than choosing a model solely by parameter count or a general leaderboard.

The lecture compares open and proprietary model ecosystems. Treat those comparisons as its May 2026 judgments. An API can reduce deployment work while limiting some engine-level control; self-hosting exposes configuration and operational responsibilities. Neither route eliminates the need to measure application quality, effective latency and failures. A service comparison should hold the task distribution and output contract fixed as far as possible.

12. Small models do not remove every systems bottleneck

Lecture 25:57

A smaller model often has fewer weight bytes and lower arithmetic demand, which can make a single-device deployment practical. But request parsing, tokenization, Python scheduling and kernel launch overhead do not necessarily shrink in proportion. At small model sizes, fixed overhead can dominate. A model-size reduction therefore requires a new profile, not just a linear latency prediction.

Multiple devices may still help an efficiency-oriented application when one device cannot fit the model and cache, or when a stringent latency target justifies parallelism. They can also hurt latency through communication. Replication and model partitioning are different levers: replication increases concurrent service capacity for independent requests; partitioning changes the execution of a model evaluation. The best choice depends on memory, bandwidth, batch size and deadlines.

The recording names several model families as practical examples. Those are dated examples, not this chapter’s recommendations or verified current winners. For the assistant, compare a short list of configurations using the same held-out extraction and dialogue cases, then measure each configuration’s service envelope. Multimodal inputs may add encoder work and variable shapes even when the language model is small.

13. Active parameters and resident parameters are different

Lecture 28:53

A capability-bound deployment may require a model whose weights occupy multiple devices. For a mixture-of-experts model, the number of parameters used for one token can be much smaller than the total parameter count. These quantities have different consequences. Active parameters affect arithmetic and routing for that token; total stored parameters affect weight residency, storage and deployment layout. Inactive experts do not automatically disappear from the system’s memory budget.

Memory fit requires weights, caches, temporary workspaces, runtime allocations and safety margin. Parallel execution requires suitable links and collective communication. A configuration that fits can still miss a deadline, while one with excellent isolated latency can sustain too little arrival traffic. Partitioning should be evaluated at the intended request mix and batch sizes.

The lecture also considers orchestration: a strong model can coordinate tools or delegate simpler subtasks to less expensive models. That proposal needs end-to-end quality evaluation. Delegation introduces error propagation, network delay and additional generations. Multiplying several measured component accuracies assumes a particular dependency structure that may not hold. Test the complete task, including failures of the delegated components.

For the maintenance assistant, a useful experiment fixes the same procedure questions and compares one large model with a coordinator-plus-extractor design. Include equipment-version conflicts and ambiguous records. Report useful-completion fraction and elapsed job time. The chapter does not infer current capability rankings from the lecture’s illustrative market discussion.

14. The engine schedules state, not just matrix multiplication

Lecture 33:04

An inference engine performs model-specific execution while managing many active sequences. Host work includes input handling, tokenization, request state, memory allocation and scheduling; device work includes numerical kernels. The host must prepare enough runnable work for the device while preserving dependencies and stopping semantics. Asynchronous submission can overlap preparation and execution when both work and resources are available.

A long prompt entering a busy replica competes with ongoing decoding. Requests that stop release memory and batch slots. Requests waiting for tools may retain context but consume no device arithmetic during that wait. These events make serving different from a fixed-shape training step. A scheduler must account for time and state, not merely pack a large tensor.

Two engine mechanisms illustrate distinct opportunities. PagedAttention, PDF pp. 3–6, allocates cached keys and values in fixed-size blocks and maps a logical sequence to possibly noncontiguous physical blocks. SGLang v1, PDF pp. 2 and 6–7, retains reusable prefix states in a radix tree with eviction and reference accounting. Block allocation reduces memory waste; prefix caching avoids recomputation. They can cooperate but are not the same optimization.

For an exact causal prefix cache, changing the prompt to increase reuse is a separate, potentially semantic change. SGLang v1 explicitly describes prompt-node rearrangement as an aggressive transformation that does not strictly preserve the original computation (PDF p. 6). Reusing unchanged states and rewriting a prompt should receive different correctness checks.

15. Engine choice is a compatibility and evidence question

Lecture 35:04

The lecture compares TensorRT-LLM, vLLM and SGLang, including their development practices and supported use cases. Those organizational assessments are Frye’s judgments. A durable selection method asks whether the required architecture, precision, decoding contract, multimodal path, hardware and monitoring are supported in the actual version being deployed.

A small educational implementation can reveal model execution and scheduling structure, but matching a toy’s equations does not certify a production runtime. Conversely, a large framework’s reputation does not guarantee support for a newly released model. Start with a pinned reference path that produces known outputs, then change one execution layer at a time. Test both outputs and stopping behavior, not merely that the server returns HTTP success.

Keep model weights, tokenizer, engine version, kernel backend, configuration and benchmark driver in the run record. When a change fails, this record gives a bounded comparison. A documentation-reading assistant may help explain source code, but claims about supported execution should be confirmed against versioned code or documentation. The references here support specific historical mechanisms; they are not a certification of today’s full framework feature set.

16. Prefill and decoding have different reuse patterns

Lecture 39:48

Prefill processes known prompt tokens and constructs their intermediate states, including the attention key/value cache. Because these input tokens are already known, many positions can be evaluated together with the required causal mask. Standard autoregressive decoding processes one newly chosen token per active sequence in an iteration. Different requests can still decode together. The distinction concerns per-sequence dependencies, not whether the whole GPU handles only one token.

For a simplified dense linear layer with $N_w$ weights, a batch of $b$ token vectors performs about $2bN_w$ floating-point operations. If weight traffic is $q_wN_w$ bytes, where $q_w$ is bytes per weight, its weight-only arithmetic intensity is approximately $2b/q_w$ operations per byte. Increasing $b$ can reuse the same weights across more arithmetic. This estimate excludes activations, KV reads, routing and other traffic, and assumes the relevant weights are fetched once per batch. It is a model of reuse, not a measurement for every architecture.

Let $F$ be operations, $D$ transferred bytes, $P_{\max}$ usable peak operations per second and $B_{\rm mem}$ usable memory bytes per second for a specified path. Resource constraints imply the ideal lower bound $t\ge\max(F/P_{\max},D/B_{\rm mem})$. The corresponding roofline upper bound on achieved operation rate is $\min(P_{\max},B_{\rm mem}F/D)$ when $D>0$. The ridge intensity $P_{\max}/B_{\rm mem}$ has units of operations per byte.

A synthetic device with $P_{\max}=10^{14}$ operations/s and $B_{\rm mem}=10^{12}$ bytes/s has ridge intensity 100 operations/byte. A step with $F=2\times10^9$ and $D=8\times10^9$ has an ideal bound of 8 ms, dominated by bytes. A step with $F=8\times10^{12}$ and the same $D$ has an 80 ms bound, dominated by arithmetic. Actual execution can be slower because dependencies, launches, communication and imperfect utilization add constraints.

The official roofline diagram (slide 28) resolves the axes and units. Its hardware table is not used as a current specification. Prefill often has higher intensity than small-batch decode, but long-context KV traffic, batching and model structure can change the bottleneck. Classify the measured configuration rather than treating phase names as a theorem.

17. Capacity, bandwidth, arithmetic and links

Lecture 42:40

Hardware selection starts with four distinct quantities: memory capacity in bytes, memory transfer bandwidth in bytes/s, arithmetic throughput in operations/s and interdevice communication performance. High-bandwidth memory, or HBM, is the device’s large, high-throughput storage tier. On-chip storage is smaller and faster. Matrix units can execute supported matrix arithmetic efficiently, while other kernels and host work may remain bottlenecks.

The package and link topology matter when a model spans devices. A high arithmetic specification does not guarantee that collectives or cache transfers are cheap. Transfer time has a latency component and a size-dependent component; a crude ideal model is $\ell+D/B$, with startup latency $\ell$ and effective bandwidth $B$. Many small transfers can therefore behave differently from one large transfer with the same total bytes.

For the assistant, memory capacity determines whether the weights and peak active caches fit; bandwidth influences low-intensity decode; arithmetic throughput influences sufficiently large prefill or verification batches; links influence partitioned execution. These requirements can conflict. A device chosen solely by peak FLOP/s may be poor for the actual workload. Specification sheets provide ceilings; measured paths provide achievable rates.

The lecture focuses on NVIDIA’s serving ecosystem and specialized matrix hardware. Statements such as “most compute is in matrix units” should be understood in that selected accelerator context, not as a universal percentage for all chips or all workloads. No numerical hardware specification is imported into the synthetic examples.

18. Hardware alternatives require workload-specific evaluation

Lecture 46:25

The recording discusses CPU, AMD and other accelerator alternatives, along with ecosystem maturity and supply constraints. Those are dated deployment judgments. They do not establish that another accelerator cannot execute Transformers or that every CPU lacks high-bandwidth memory. Software support, supported precision, batch size, memory layout and deployment scale influence the comparison.

For a solo application, a locally available device may meet a modest arrival rate more economically than a scarce high-end accelerator, even when its isolated latency is higher. For a stringent interactive target, a faster device may be necessary. The correct comparison holds the quality contract and actual workload fixed, includes allocation and startup costs, and reports achievable performance. The lecture provides practical experience, not a benchmark of every hardware alternative.

19. Network distance and failure change the service envelope

Lecture 49:09

Device computation is only part of end-to-end latency. Geographic distance, network transport and request routing add delay. The lecture’s millisecond examples illustrate orders of magnitude; they are not guaranteed latencies for arbitrary routes. In interactive applications, a modest device improvement may be hidden by a larger network delay. Measure at the user boundary as well as inside the replica.

Frye reports operational GPU reliability challenges. The accompanying Modal engineering article, December 28, 2025, describes its fleet’s light boot checks, ongoing passive checks and periodic active checks. Passive checks observe signals such as error logs; active checks run work and may require exclusive device access. This is a particular operator’s experience, not a universal component-lifetime distribution.

Slide 34 shows an H100 mean-time figure of roughly 50 days with an “annual failure rate” near 700%. A probability cannot exceed 100%. If 50 days is interpreted as the mean interval of a stationary event process, $365/50=7.3$ is an expected count of events per year. Under an additional Poisson assumption, the probability of at least one event would be $1-e^{-7.3}\approx0.9993$. These are different quantities. The slide does not specify enough sampling detail to infer a universal H100 failure probability or unrecoverable-device lifetime.

Independent inference replicas can often continue serving when one is drained, but capacity then falls. Retries add demand and may duplicate work. For the assistant, assess the reduced-capacity state as well as the all-healthy state; define a request identifier and completion contract for retry handling. Reliability is an operational property of the whole service, not just the chip.

20. Autoscaling is delayed capacity control

Lecture 51:29

A fixed allocation sized for peak demand sits partly idle between peaks. Autoscaling changes the number of replicas as demand changes. But new capacity is useful only after machines are available, containers start and the model service becomes ready. A fast decision to scale does not imply a fast increase in serving capacity.

Consider a synthetic burst lasting 20 seconds that requires four replicas when only one is ready. If a new replica takes 60 seconds to become usable, reactive scale-up cannot help that burst. If readiness takes five seconds, scale-up can help the remaining interval, while the first five seconds still require buffering, admission control or reserve capacity. These are deliberately simple timing examples; they do not predict a cloud deployment.

Warm reserve capacity exchanges idle expenditure for shorter reaction delay. A shared platform can pool reserve devices across workloads, but correlated demand reduces the benefit of pooling. A fleet that serves many applications does not automatically achieve perfect statistical multiplexing. Distinguish allocation utilization—useful running time divided by paid allocated time—from kernel activity and achieved arithmetic throughput. A device can be allocated and busy while still performing little useful work.

21. Move startup work out of the critical path

Lecture 53:44

The May 12, 2026 Modal article explains four cooperating mechanisms: a buffer of ready machines, lazy loading from a content-addressed filesystem cache, host-memory snapshots and device-state snapshots. They target different parts of readiness time. The article’s speedups are its reported deployment measurements, not results reproduced here.

A lazy filesystem avoids waiting for files the application never reads. It still must supply every byte that is actually accessed. A content-addressed cache identifies data by content so that identical bytes can be reused across images. Eager prefetch can complement lazy access for common libraries. “Lazy” therefore means moving or avoiding work based on demand, not eliminating necessary data transfer.

Checkpoint/restore saves enough process state to resume execution instead of repeating initialization. Host state includes memory mappings, thread state and file descriptors; device state includes allocations and execution resources. The article describes gVisor-based host snapshots, rather than claiming Modal simply uses CRIU for its current implementation. It also discusses device support and compatibility limitations. The teaching principle is to preserve a valid execution state across restoration, not to assume arbitrary processes are automatically portable.

Weight bytes still need to be loaded or otherwise made available. Snapshots can bypass expensive setup whose output is small, but cannot defeat bandwidth limits for large necessary transfers. The article separately notes environment compatibility, multi-GPU coordination and model-engine adjustments. A restored service must pass the same output and readiness checks as a freshly initialized service. When it reopens external resources or restores devices differently, the correctness contract must include those transitions.

Cold-start latency is not steady-state token latency. A service can have excellent decoding after warm-up and still fail short demand spikes because readiness is slow. Report both, together with the definition of “ready”: a running container, loaded weights, or a replica that has successfully handled a representative request are different milestones.

22. Classify the defect before tuning it

Lecture 57:04

Frye distinguishes application bugs, model bugs and performance bugs. An application bug may construct the wrong prompt or misparse tool arguments. A model-quality failure may persist even under correct reference execution. A performance defect may preserve answers but cause unacceptable delay. Classification is a hypothesis to test, not a label inferred from the symptom alone.

For the assistant, an answer citing an obsolete manual could arise from retrieval, template construction, cached state, generation or downstream parsing. Capture an exact synthetic reproducer and compare the effective token prefix and reference output. If the reference fails in the same way, a kernel rewrite is unlikely to repair the quality issue. If only one engine fails under the same contract, inspect numerical execution, supported architecture details and stopping behavior.

Real traffic differs from a small demonstration in lengths, special tokens, conflicting context and concurrency. A model that passes an isolated prompt may fail after a configuration update. Test these dimensions deliberately. The lecture’s practical warnings about recent model support motivate validation; they do not establish that every new open model has a defective implementation.

23. Observability is evidence for diagnosis

Lecture 59:07

Observability means having measurements that reveal relevant internal behavior. In this chapter, a request record links its arrival, effective token input, model/tokenizer/template versions, scheduling events and emitted tokens. Logs of only the original text can miss template or tokenization changes. A bounded synthetic fixture gives an exact record without depending on undisclosed production examples.

The lecture invokes the mathematical relationship between observability and controllability. For a finite-dimensional discrete linear system with column state $z_r\in\mathbb R^d$, output $y_r\in\mathbb R^{n_y}$, known matrices $A\in\mathbb R^{d\times d}$ and $C\in\mathbb R^{n_y\times d}$, and no unknown inputs, write $z_{r+1}=Az_r$, $y_r=Cz_r$. The initial state is observable from finitely many outputs when the stacked matrix $[C;CA;\ldots;CA^{d-1}]$ has rank $d$, where $d$ is state dimension. Transposing this matrix gives the controllability matrix of the dual pair $(A^\top,C^\top)$. The equality of ranks establishes the linear duality.

This formal result does not imply that adding arbitrary logs makes a nonlinear serving system identifiable or controllable. Two faults can produce the same aggregate metric. A useful diagnostic links a symptom to a proposed mechanism and then changes a controlled variable or inspects a trace that distinguishes alternatives. For example, a long TTFT could arise from queue delay, tokenization, prefill, cold start or transport; first isolate the interval that increased.

Versioned request records make failures reproducible. They do not by themselves prove causality. When a mitigation works, record the observed effect and the still-unproven root cause separately.

24. Evaluations survive model swaps only when the task is stable

Lecture 61:12

An application evaluation asks whether the system fulfills a task. It can remain useful when a model or engine changes, provided the task specification and reference labels remain valid. For the assistant, evaluation cases might include identifying a manual revision, extracting an inspection date and refusing to combine incompatible equipment records. These tests express application behavior, not a preference for one model’s prose.

Separate exact checks from judged checks. A date field can be compared exactly after an explicit normalization rule. A grounded explanation may require checking whether each cited procedure supports the answer. A numerical throughput target requires a controlled load test. An aggregate score should preserve these dimensions so that an optimization does not trade away an essential capability unnoticed.

Passing a finite evaluation is evidence for its tested population, not proof of general reliability. Repeated stochastic generations require specifying sampling settings and trial count. A model-independent task test is durable only while its task assumptions hold; new equipment, tool behavior or traffic can require new cases. Use held-out cases to assess selection decisions and keep diagnostic failures for regression tests.

25. Measure the request path and the device path

Lecture 62:54

Request telemetry should separate queue delay, preprocessing, uncached/cached prefill, decoding, transport and external-tool time where those boundaries can be measured. Fleet telemetry should report offered and completed rate, active sequences, memory pressure, cache behavior and replica readiness. Device telemetry adds kernel activity, power, temperature and communication traces. Each measurement needs units and a population.

Large prompt loads can increase decoder gaps; low aggregate request rate can reflect slow tools rather than an idle application; a hot device can slow arithmetic; a memory-constrained scheduler can limit concurrent work. A dashboard correlation is a lead, not a diagnosis. The lecture’s dashboard and straggler examples demonstrate investigative practice. No unseen production logs are reconstructed in this chapter.

Kernel activity measures how much of the sample interval has a kernel running. It does not tell whether matrix units are saturated or whether the application uses its paid allocation efficiently. Similarly, an average temperature can hide one throttled device in a multidevice replica. Retain per-device and per-request information for the questions they answer, then aggregate deliberately.

For a simple queue model, let arrivals be Poisson with rate $\lambda$, independent service times exponential with rate $\mu$, one FCFS server, and no finite capacity or abandonment. Under $0\le\lambda<\mu$, the stationary occupancy distribution is $(1-\rho)\rho^n$, with $\rho=\lambda/\mu$. Its mean is $\rho/(1-\rho)$, obtained by summing the geometric-series derivative. The steady-state flow relation $L=\lambda W$ then gives mean total response time $W=1/(\mu-\lambda)$ for $\lambda>0$, with limit $1/\mu$ at zero arrival rate.

With $\mu=4$ requests/s, loads $\rho=0.5,0.9,0.99$ give mean responses $0.5,2.5,25$ seconds. This is an original analytic queue example, not a GPU service prediction. Real batching changes service dynamics; request lengths are heterogeneous; timeouts, finite queues and autoscaling alter the assumptions. Its lesson is that utilization and delay can have a nonlinear relationship. At $\lambda\ge\mu$ the stated infinite-buffer model has no stationary finite response mean.

26. Optimization changes a coupled system

Lecture 66:56

The lecture organizes performance work around speculative decoding, quantization, host overhead and kernels. These levers address different costs and can interact. A faster kernel can expose host scheduling as the next bottleneck. Quantization can release memory for a larger batch, which changes decode arithmetic intensity and queueing. Speculation adds verification work and a draft model, which changes memory occupancy and scheduling.

Do not multiply isolated speedup factors without a model of their overlap. If two improvements both remove the same half of runtime, applying both cannot remove that half twice. Begin with an end-to-end profile and an output-equivalence or quality contract. After each change, rerun the same workload and inspect both the target metric and other binding constraints.

27. Exact speculative sampling preserves a distribution

Lecture 67:54

A draft model proposes tokens cheaply; the target model evaluates candidate prefixes together. Parallel verification does not require trusting the draft. It requires accepting and correcting proposals so that the emitted output follows the target distribution. For greedy decoding, a matching prefix can be retained before the target’s first disagreement. For stochastic decoding, matching the target’s most likely token is insufficient.

At a fixed prefix, let $p$ and $q$ be normalized target and draft distributions over a finite common vocabulary $\mathcal V$, after the chosen temperature or support transformations. Draw $x$ from $q$. When $q(x)>0$, accept with probability $\min(1,p(x)/q(x))$. The unconditional accepted mass at $x$ is $\min(p(x),q(x))$. Define residual mass $r(x)=\max(p(x)-q(x),0)$ and $R=\sum_xr(x)$.

The total rejection probability equals $R$, because both $p$ and $q$ sum to one. If rejection occurs and $R>0$, draw from $r/R$. The final probability of emitting $x$ is therefore

\[ \min(p(x),q(x))+R\frac{r(x)}R=p(x). \]

This is a direct proof of the correction rule in Leviathan, Kalman and Matias, ICML 2023, PDF pp. 2–4. Tokens with $q(x)=0$ are never proposed, so the acceptance ratio is not evaluated there; their positive target mass is supplied by the residual. If $p=q$, $R=0$ and rejection cannot occur. No residual normalization is needed.

For $p=(0.6,0.3,0.1)$ and $q=(0.2,0.3,0.5)$, accepted masses are $(0.2,0.3,0.1)$, rejection probability is $0.4$ and the residual puts all mass on the first token. The emitted distribution is exactly $p$. Simply discarding rejected drafts and sampling again from $p$ would instead yield $(0.44,0.42,0.14)$; that naive fallback is biased.

For a drafted block, verification evaluates target conditionals at its successive candidate prefixes. Retain an accepted prefix; at the first rejection, discard later draft tokens and emit a residual-corrected token. If all drafted tokens pass, emit one additional target token. Induction over emitted prefixes preserves the full autoregressive target distribution under exact arithmetic and the stated sampling contract. The original algorithm drafts autoregressively; other proposal structures require their own corresponding verification proof.

For a simplified block with $k$ proposed tokens and independent, constant acceptance probability $\alpha$, expected progress including the correction or bonus token is $A_k=\sum_{r=0}^k\alpha^r$. For $\alpha<1$, this equals $(1-\alpha^{k+1})/(1-\alpha)$; at $\alpha=1$ it is $k+1$. Assume verification costs one target-step time and each sequential draft step costs fraction $c$ of that time. For long enough generation, the ideal speedup is $A_k/(1+kc)$. These are the original paper’s simplifying cost assumptions, not a production invariant.

With $k=4$, $c=0.1$ and $\alpha=0.8$, the ideal factor is $3.3616/1.4\approx2.401$. At $\alpha=0$ it is $1/1.4<1$: correct speculation can be slower. At $\alpha=1$ it is $5/1.4\approx3.571$. Progress is bounded by $k+1$ per verification; it is not an unbounded exponential speedup in block length. Target verification can become more expensive with longer blocks or concurrent load, so measure the actual cost rather than assuming it is fixed.

28. Improving the draft is a cost–acceptance tradeoff

Lecture 71:32

A draft may come from a small neural model, a model’s auxiliary prediction heads, repeated n-grams or a known predicted continuation. The objective is not merely to minimize draft latency or maximize token agreement in isolation. It is to increase accepted progress per total drafting-and-verification time while preserving the output contract. A larger draft can improve acceptance but consume enough memory or time to lose the benefit.

DFlash v1, February 2026, PDF pp. 3–5, proposes parallel block drafting conditioned on target hidden features. The target’s selected hidden representations are fused; projected context is injected into the draft layers’ key/value conditioning; masked future positions are predicted in a block. This shifts drafting away from repeated sequential draft passes. The model is trained against a frozen target with a matching block-oriented objective.

These hidden states are computational features, not proof that the system represents human-like future “ideas.” The paper’s design supports a mechanism for improved proposal quality. It does not identify a unique cognitive interpretation. Its results also depend on target, task, backend, block size and temperature. For example, Table 1 on PDF p. 6 reports Qwen3-8B nonthinking Transformers-backend averages of $4.86\times$ for greedy decoding and $4.03\times$ at temperature one across its listed tasks, using H200s unless otherwise specified. Those are the authors’ reported comparisons, not a universal $6\times$ or a local reproduction.

The exact single-token proof in the preceding section is not a blanket certification of every tree or parallel-block implementation. A proposal’s joint distribution, its available probabilities, attention mask and correction rule must agree with the chosen sampling procedure. Non-greedy settings require particular care with temperature, top-$k$, top-$p$ and penalties. “Lossless” should always identify the target behavior and arithmetic assumptions being preserved.

29. Fewer bits change memory and numerical behavior

Lecture 73:43

Quantization represents selected tensors with fewer bits, often with scale metadata and conversion operations. If weight storage changes from eight to four bits per element, its packed payload halves before metadata and layout overhead. End-to-end latency does not necessarily halve: other traffic and work remain, kernels may differ, and conversion can add overhead. Weight precision, activation precision and KV-cache precision are separate choices.

Let a fraction $f$ of an original runtime be weight-transfer time and suppose only that part is sped up by factor $r$, with all other time unchanged and additive. The overall speedup is $1/((1-f)+f/r)$. With $f=0.6$ and $r=2$, it is approximately $1.429$, not two. The assumptions exclude bottleneck migration and batching changes, so this is a sensitivity calculation rather than a performance forecast.

The lecture warns that cached states can be harder to quantize without quality changes. It would be too strong to conclude that KV-cache quantization always requires retraining. KIVI v1, PDF pp. 1–4, is a concrete counterexample: a tuning-free method that quantizes key cache per channel and value cache per token, with grouped low-precision portions and residual full-precision portions to handle streaming. Its design and tested outcomes are specific, not proof that arbitrary cache precision is harmless.

For a standard full-history key/value cache, define layer count $L$, KV-head count $H_{\rm kv}$, per-head dimension $d_h$, bytes per stored element $q_{\rm kv}$ and stored sequence lengths $s_j$. Ignoring metadata, padding and sharding, the logical payload is

\[ M_{\rm KV}=2LH_{\rm kv}d_hq_{\rm kv}\sum_js_j. \]

The factor two accounts for keys and values. Grouped-query attention shares KV heads across several query heads, so substituting the number of query heads can overcount. Sliding-window attention, latent caches and hybrid state-space models require different formulas. Stored positions should be counted explicitly: an emitted last token need not have its KV state computed if decoding stops before consuming it.

For $L=32$, $H_{\rm kv}=8$, $d_h=128$, $q_{\rm kv}=2$ and two stored lengths 17 and 31, the payload is $6{,}291{,}456$ bytes. Allocating blocks of 16 tokens rounds each sequence to 32 slots, yielding $8{,}388{,}608$ bytes before metadata. Block allocation limits waste but does not eliminate last-block slack. Quantized caches additionally need scales, packing, residual portions and compatible kernels.

For the assistant, evaluate long contexts, revision conflicts, numerical fields and stopping behavior under each precision configuration. Small average score changes can conceal task-specific failures. If a target distribution is altered by quantization, speculation may preserve that quantized target’s distribution; it does not recover the original full-precision distribution automatically.

30. Keep the host from starving the device

Lecture 76:21

Host overhead occurs when useful device work waits for host preparation or synchronization. The November 18, 2025 Modal article discusses reducing avoidable transfers, kernel launch overhead and repeated submission. An idle device interval is a symptom: it may also arise because dependencies, communication, admission limits or input availability prevent progress. A trace must identify which cause is active.

Kernel fusion combines operations into a single kernel, potentially reducing launches and intermediate traffic. A CUDA graph instead represents operations and their dependencies as a reusable launchable object. CUDA 12.8 programming guide §3.2.8.7 separates graph definition, instantiation and repeated execution. A graph launch can reduce host setup without merging all device kernels into one. Shape changes, pointer lifetimes and unsupported captured operations can require updates or different graphs.

The lecture shows a multidevice straggler and hypothesizes placement or host effects. A low-power device or a delayed timeline is evidence of unequal progress; it does not establish the root cause. Compare per-device traces, host scheduling and communication boundaries. When one participant stalls a collective, other devices may appear underutilized even if their own kernels are efficient.

A concrete original May 4, 2026 Modal case study reports profiling Qwen2.5-VL-3B-Instruct on an H100 with SGLang. Reopening shared CUDA storage repeatedly in the host path was replaced by caching pool handles. The reported end-to-end measurements improved; the teaching point is that a host bookkeeping change can affect decoding even when discovered in input processing. These measurements are vendor-reported, not reproduced by this chapter’s Python example.

For a production experiment, first confirm that requests are waiting and the device could usefully proceed. Then profile the host and device timelines before rewriting low-level kernels. If a fixed host cost is on the critical path, optimizing arithmetic alone cannot remove it. After a change, measure end-to-end completion and tail gaps; a vanished hotspot alone does not establish an application win.

31. Approximate execution needs its own acceptance contract

Lecture 79:56

Layer skipping, pruning or approximate speculation can change model outputs. Such approaches may be acceptable for an application, but the claim is then a quality–performance tradeoff rather than exact distribution preservation. Test the actual task and define an acceptable quality loss. A favorable average can still conceal failure on important subsets.

The lecture anticipates specialization of prefill and decode hardware. A nearby systems result shows that phase specialization can also occur through scheduling and placement. DistServe v1, PDF pp. 1–4, separates prefill and decode onto different resources, allowing independent allocation at the cost of state transfer. Sarathi-Serve v1, PDF pp. 1–4, chunks prefills to admit new work while limiting interruption of ongoing decoding. These are related research extensions, not new technical material attributed to this part of the recording.

Disaggregation adds a KV transfer path and potentially duplicates model residency; chunking changes scheduling granularity and can affect TTFT. Neither method is uniformly best. Compare their joint timing constraints, memory and network assumptions for the actual workload. Predictions about future optical, analog or specialized devices remain proposals; the chapter does not treat them as current deployed capabilities.

33. A finite serving laboratory

The original standard-library program below computes timestamp metrics, simulates one FCFS server, counts full-history KV storage and enumerates the mass correction for speculative sampling. It also evaluates the ideal roofline and block-cost examples. It uses hypothetical inputs, no model weights, no network and no GPU. It is a mechanism check, not a benchmark of vLLM, SGLang, Modal or any accelerator.

The FCFS simulator uses ordered arrival times and positive service durations. It reports waiting, response, start and completion times. A simultaneous burst and evenly spaced arrivals have different delays despite identical service work. The M/M/1 function is separate: it calculates a stationary analytic mean under the stated Poisson/exponential assumptions. It does not fit those assumptions to the finite simulator.

The categorical routine enumerates probabilities instead of relying on Monte Carlo noise. It checks equal distributions and disjoint support as well as a mixed example. The cost routine includes the bonus token and handles acceptance one without division by zero. Input checks distinguish integer counts from probabilities and reject nonfinite values. Larger arrays and extreme numerical magnitudes require additional engineering; these small finite fixtures do not validate a neural implementation.

Save the linked file and run python chapter09.py. Change the arrival pattern, stored sequence lengths or categorical draft distribution to see which conclusions depend on the workload. The code deliberately returns no TPOT for a one-token response.

Original chapter09.py

"""Original finite serving models. No GPU, model, network or framework required."""
import math


def finite(value, *, positive=False):
    if isinstance(value, bool) or not isinstance(value, (int, float)):
        raise ValueError('expected a finite number')
    if not math.isfinite(value) or (value <= 0 if positive else value < 0):
        raise ValueError('number outside its nonnegative/positive domain')
    return value


def count(value, *, positive=False):
    if isinstance(value, bool) or not isinstance(value, int):
        raise ValueError('expected an integer')
    return finite(value, positive=positive)


def token_metrics(arrival, timestamps):
    finite(arrival)
    if not timestamps:
        raise ValueError('a completed request needs at least one token')
    times = [finite(t) for t in timestamps]
    if times[0] < arrival or any(b < a for a, b in zip(times, times[1:])):
        raise ValueError('timestamps must follow arrival and be ordered')
    gaps = [b-a for a, b in zip(times, times[1:])]
    return dict(ttft=times[0]-arrival, ttl=times[-1]-arrival, gaps=gaps,
                tpot=sum(gaps)/len(gaps) if gaps else None)


def quantile(values, probability):
    """Empirical nearest-rank convention, including min at probability zero."""
    finite(probability)
    if probability > 1 or not values:
        raise ValueError('probability in [0,1] and nonempty samples required')
    ordered = sorted(finite(x) for x in values)
    return ordered[max(0, math.ceil(probability*len(ordered))-1)]


def fcfs(arrivals, services):
    """One work-conserving FCFS server, seconds, no preemption or batching."""
    if len(arrivals) != len(services):
        raise ValueError('one service time per arrival required')
    a = [finite(x) for x in arrivals]
    s = [finite(x, positive=True) for x in services]
    if any(y < x for x, y in zip(a, a[1:])):
        raise ValueError('arrivals must be ordered')
    available, rows = 0.0, []
    for arrival, service in zip(a, s):
        start = max(available, arrival)
        available = start + service
        rows.append((start-arrival, available-arrival, start, available))
    return rows


def mm1_mean(arrival_rate, service_rate):
    """Stationary M/M/1 response mean; deliberately not a GPU simulator."""
    finite(arrival_rate)
    finite(service_rate, positive=True)
    if arrival_rate >= service_rate:
        raise ValueError('no stationary response mean at load >= 1')
    return 1/(service_rate-arrival_rate)


def kv_bytes(layers, kv_heads, head_dim, bytes_per_element, lengths, block=1):
    for n in (layers, kv_heads, head_dim, block):
        count(n, positive=True)
    finite(bytes_per_element, positive=True)
    lengths = [count(n) for n in lengths]
    slots = sum(((n+block-1)//block)*block for n in lengths)
    return 2*layers*kv_heads*head_dim*bytes_per_element*slots


def roofline_seconds(flops, moved_bytes, peak_flops, bandwidth):
    for x in (flops, moved_bytes):
        finite(x)
    for x in (peak_flops, bandwidth):
        finite(x, positive=True)
    return max(flops/peak_flops, moved_bytes/bandwidth)


def categorical(values):
    if not values:
        raise ValueError('nonempty categorical distribution required')
    values = tuple(finite(x) for x in values)
    if not math.isclose(math.fsum(values), 1.0, rel_tol=0, abs_tol=1e-12):
        raise ValueError('probabilities must sum to one')
    return values


def speculative_distribution(target, draft):
    """Enumerate accepted and residual mass, rather than Monte Carlo sampling."""
    p, q = categorical(target), categorical(draft)
    if len(p) != len(q):
        raise ValueError('target and draft need the same token alphabet')
    accepted = tuple(min(a, b) for a, b in zip(p, q))
    residual_mass = tuple(max(a-b, 0) for a, b in zip(p, q))
    rejection = math.fsum(residual_mass)
    residual = tuple(x/rejection for x in residual_mass) if rejection else None
    emitted = tuple(a+b for a, b in zip(accepted, residual_mass))
    assert all(math.isclose(a, b, abs_tol=1e-12) for a,b in zip(emitted,p))
    return accepted, rejection, residual, emitted


def block_speedup(acceptance, draft_tokens, relative_draft_cost):
    """IID constant acceptance; verification cost one target step; bonus token."""
    finite(acceptance)
    count(draft_tokens)
    finite(relative_draft_cost)
    if acceptance > 1:
        raise ValueError('acceptance in [0,1] required')
    advance = math.fsum(acceptance**i for i in range(draft_tokens+1))
    return advance/(1+draft_tokens*relative_draft_cost)


def main():
    trace = token_metrics(0, [0.4,0.42,0.44,0.9])
    print('Trace TTFT/TPOT/TTLT:', *(f'{trace[k]:.6f}' for k in ('ttft','tpot','ttl')))
    print('Trace p50/p95 gap:', quantile(trace['gaps'],.5), quantile(trace['gaps'],.95))
    assert token_metrics(1,[1.5])['tpot'] is None
    smooth = fcfs([0,1,2,3], [0.75]*4)
    burst = fcfs([0,0,0,0], [0.75]*4)
    print('FCFS smooth/burst response means:',
          *(f'{sum(r[1] for r in rows)/4:.6f}' for rows in (smooth,burst)))
    print('M/M/1 means at loads .5/.9/.99:',
          *(f'{mm1_mean(4*r,4):.6f}' for r in (.5,.9,.99)))
    exact=kv_bytes(32,8,128,2,[17,31])
    paged=kv_bytes(32,8,128,2,[17,31],block=16)
    print('KV exact/paged bytes:',exact,paged)
    print('KV fourfold query-head substitution error:',kv_bytes(32,32,128,2,[17,31])/exact)
    print('Roofline decode/prefill seconds:',
          *(f'{roofline_seconds(f,d,1e14,1e12):.6f}' for f,d in ((2e9,8e9),(8e12,8e9))))
    print('Weight-only halving, original weight fraction .6:',f'{1/(.4+.6/2):.6f}')
    p,q=(.6,.3,.1),(.2,.3,.5)
    accepted,rejected,residual,emitted=speculative_distribution(p,q)
    print('Speculative accepted/rejection/residual:',accepted,f'{rejected:.6f}',residual)
    print('Speculative corrected output:',tuple(round(x,6) for x in emitted))
    assert speculative_distribution(p,p)[2] is None
    assert speculative_distribution((1,0),(0,1))[3] == (1,0)
    for a in (0,.5,.8,1):
        print(f'Block k=4, draft cost .1, acceptance {a:g}: {block_speedup(a,4,.1):.6f}')
    assert fcfs([],[]) == []
    assert kv_bytes(1,1,1,2,[]) == 0
    assert roofline_seconds(0,0,1,1) == 0
    assert block_speedup(1,0,0) == 1
    invalid = [lambda: token_metrics(0,[]),lambda: token_metrics(1,[.5]),
        lambda: token_metrics(0,[1,.5]),lambda: quantile([], .5),
        lambda: quantile([1],1.1),lambda: fcfs([1,0],[1,1]),
        lambda: fcfs([0],[0]),lambda: fcfs([0],[]),
        lambda: mm1_mean(4,4),lambda: mm1_mean(-1,4),
        lambda: kv_bytes(1,1,1,2,[1],0),lambda: kv_bytes(1,1,1,2,[1.5]),
        lambda: roofline_seconds(1,1,0,1),lambda: categorical([.1,.2]),
        lambda: categorical([float('nan'),1]),lambda: speculative_distribution([1],[0,1]),
        lambda: block_speedup(1.1,4,.1),lambda: block_speedup(.5,True,.1)]
    for call in invalid:
        try: call()
        except ValueError: pass
        else: raise AssertionError('invalid input accepted')
    print('Boundary cases and',len(invalid),'invalid-input cases passed.')


if __name__ == '__main__':
    main()

34. Six problems with complete solutions

1. A latency report with the wrong denominator

A request arrives at zero and emits tokens at 0.40, 0.42, 0.44 and 0.90 seconds. Compute TTFT, TTLT and TPOT using this chapter’s definition. A colleague divides the last-minus-first interval by four. Identify the error. Explain why mean TPOT alone does not certify smooth streaming and how a one-token request should be handled.

Solution

TTFT is 0.40 s and TTLT is 0.90 s. Three post-first intervals sum to 0.50 s, so TPOT is $0.50/3\approx0.166667$ s. The colleague’s $0.125$ s divides by token count rather than gap count. The telescoping identity is $0.40+3(0.166667)\approx0.90$; using the wrong denominator fails that identity.

The gaps are 0.02, 0.02 and 0.46 s. Their median is 0.02 s, while the nearest-rank p95 is 0.46 s for this three-element sample. Neither this small-sample p95 nor the average predicts an unmeasured deployment; they reveal the conspicuous final stall in this trace. Record a request-level “any gap over threshold” indicator for smoothness. A one-token response has no post-first interval, so its TPOT is undefined and it should be excluded from the TPOT mean with its count reported separately.

2. Same work, different queues

A single FCFS server requires 0.75 s for each of four requests. Compare arrivals at 0, 1, 2 and 3 s with four simultaneous arrivals at zero. Derive all completion times and mean response times. Separately, for a stationary M/M/1 model with service rate four requests/s, compute the mean at loads 0.5 and 0.99. Explain why neither the burst trace nor the M/M/1 result determines a GPU service’s capacity.

Solution

For ordered arrivals, $s_j=\max(a_j,c_{j-1})$ and $c_j=s_j+0.75$, with the server initially free. Evenly spaced arrivals produce completions 0.75, 1.75, 2.75 and 3.75 s. Every response takes 0.75 s. The burst completes at 0.75, 1.50, 2.25 and 3.00 s, giving mean response $(0.75+1.50+2.25+3.00)/4=1.875$ s. Service work is unchanged; waiting changes.

For M/M/1, $\lambda=\rho\mu$. At load 0.5, $W=1/(4-2)=0.5$ s. At load 0.99, $W=1/(4-3.96)=25$ s. This model assumes independent exponential service, Poisson arrivals, one server and stationary stable load. The deterministic four-request trace satisfies different assumptions and is not its sample mean prediction. Real engines batch requests, overlap phases, constrain caches and may scale replicas. The calculations isolate queueing effects; actual capacity must be measured against a specified workload and SLO.

3. Cache bytes, query heads and block slack

A full-history cache has 32 layers, eight KV heads, 128 elements per head and two bytes per element. Two sequences have 17 and 31 stored positions. Compute payload with exact allocation and with blocks of 16 tokens. There are 32 query heads. Show the error from substituting that count. State at least three costs or architectural conditions omitted by the formula.

Solution

Bytes per stored position are $2\cdot32\cdot8\cdot128\cdot2=131{,}072$. Exact allocation has 48 positions and therefore 6,291,456 bytes, or 6 MiB. Each sequence needs two blocks of 16; total allocated slots are 64 and bytes are 8,388,608, or 8 MiB. Slack is 16 slots, 2 MiB. It is 25% of the allocated payload, or one third of the exact logical payload; the denominator must be stated.

Using 32 query heads instead of eight KV heads multiplies the count by four because grouped-query attention shares KV states across query heads. The expression excludes block tables, scales/packing for quantization, allocator/runtime workspaces, model weights and device sharding or replication. It assumes every layer uses the same standard full-history KV form. Sliding windows, latent caches or hybrid state-space layers need architecture-specific counts. Finally, stored positions are not automatically prompt plus emitted output: the last emitted token may never be consumed into the cache.

4. A roofline and a disappointing precision change

A hypothetical device has usable ceilings $10^{14}$ operations/s and $10^{12}$ bytes/s. For $F=2\times10^9$ operations and $D=8\times10^9$ bytes, compute the ideal time bound and ridge intensity. If only 60% of a measured additive runtime is weight transfer and halving its bytes halves that component’s time, compute total speedup. Explain why this remains conditional even after checking the arithmetic.

Solution

The arithmetic bound is $2\times10^{-5}$ s, or 20 microseconds; the memory bound is $8\times10^{-3}$ s, or 8 ms. The resource lower bound is their maximum, 8 ms. Ridge intensity is $10^{14}/10^{12}=100$ operations/byte, while this workload’s intensity is 0.25 operations/byte. It is memory-dominated in this ideal model.

Normalize measured runtime to one. Unchanged work is 0.4, and the improved weight-transfer component is 0.6/2=0.3, giving new time 0.7 and speedup $1/0.7\approx1.428571$. This assumes component additivity, unchanged nonweight work, unchanged effective bandwidth and no new conversion overhead. Quantization can change kernels, batch size and quality, while real execution can have overlapping costs. A roofline ceiling is not a measured operating point. Check the output contract and rerun the end-to-end workload before claiming the predicted benefit.

5. Prove correction and expose the biased fallback

Let target probabilities be $(0.6,0.3,0.1)$ and draft probabilities $(0.2,0.3,0.5)$. Compute proposal acceptance probabilities, unconditional accepted mass, rejection probability and corrected residual distribution. A developer samples from the target directly after every rejection. Derive the resulting distribution and explain its failure. For $k=4$, $\alpha=0.8$ and relative sequential draft cost 0.1, compute ideal block speedup and list its essential assumptions.

Solution

Acceptance probabilities for proposed tokens are $(1,1,0.2)$. Multiplying by draft probabilities gives accepted mass $(0.2,0.3,0.1)$, whose sum is 0.6. Rejection probability is 0.4. Positive target-minus-draft mass is $(0.4,0,0)$; normalization yields residual $(1,0,0)$. Adding its unconditional contribution recovers $(0.6,0.3,0.1)$.

Direct target fallback contributes $0.4p=(0.24,0.12,0.04)$, so the wrong output distribution is $(0.44,0.42,0.14)$. It oversupplies tokens already sufficiently represented by accepted proposals and undersupplies the first. In general, $\min(p,q)+\max(p-q,0)=p$ pointwise. This also handles zero draft mass without evaluating a ratio there; if $p=q$, rejection mass is zero.

The ideal accepted progress is $1+0.8+0.64+0.512+0.4096=3.3616$ tokens, including correction/bonus. Cycle time is $1+4(0.1)=1.4$ target-step units, so speedup is $2.401143$. It assumes IID constant acceptance, fixed verification cost, sequential draft cost proportional to block length, adequate parallel compute and sufficiently long outputs. Context-dependent acceptance, target-batch overhead, concurrency and memory pressure can change the result. The correctness proof and the speedup model are separate claims.

6. Design a defensible serving comparison

The maintenance assistant combines interactive chat, a multistep tool agent and a bulk extraction job. Propose an experiment comparing a cached-prefix engine, a quantized variant and a speculative variant. The team reports that TTFT and TPOT each pass for 95% of requests, averages p99 across replicas, and claims a 700% annual failure probability from a 50-day mean event interval. Repair these three claims. Explain how automated implementation search should use your experiment.

Solution

Freeze model/tokenizer/template/stop/sampling revisions and representative task cases. Specify arrival schedules and joint input/output lengths, then stratify the three workload types. Use open-loop offered-load sweeps for capacity, measure from scheduled arrivals, and record successful completions, timeouts, cancellations and queue growth. Keep readiness/cold-start trials separate. Record per-request first/last timestamps and individual token gaps, as well as per-device state and cache memory. Repeat runs with explicit warm-up and trial count.

For unchanged-prefix reuse, compare outputs under the same effective token and modality context and test invalidation after version changes. For quantization, evaluate task quality separately because the target numerical behavior changes. For exact speculation, check the appropriate sampling correction and target conditionals; then measure draft/verification cost and accepted progress. A finite checker should include boundary cases and held-out workload mixtures, while remaining bounded evidence rather than full semantic proof.

Marginal 95% passes guarantee only at least 90% joint success by the union bound; measure the joint per-request event. Fleet p99 must come from appropriately pooled samples/histograms, not a mean of replica percentiles. A 50-day mean event interval corresponds to 7.3 expected annual events under stationary rate interpretation, not a probability of 730%. With an additional Poisson assumption the probability of at least one event is $1-e^{-7.3}\approx99.93\%$; the lecture’s figure alone does not certify that assumption or universal device reliability.

Automated search may alter candidate implementations while the reference, checker and benchmark remain controlled. Reject incorrect candidates before performance ranking, include the same accounting of failed or dropped work, and use held-out cases to detect benchmark specialization. A faster tested candidate is a validated improvement within the measured contract; deploying it under new traffic requires renewed evidence.
